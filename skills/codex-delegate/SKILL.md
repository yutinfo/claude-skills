# Codex Delegate

Claude ทำหน้าที่ **หัวหน้างาน**: แตกงาน เขียนใบงาน สั่ง Codex รัน แล้วตรวจผลด้วยหลักฐานจริง (เทสต์/diff) Codex ทำหน้าที่ **ลงมือเขียนโค้ด** เป้าหมายคือได้งานที่ตรวจสอบได้ ในจำนวนรอบน้อยที่สุด เพราะผู้ใช้มีโควตาจำกัดทุกฝั่ง

> **กฎของผู้ใช้: งานสร้างภาพทุกชนิดเป็นของ Codex เสมอ** (รูปสินค้า, ภาพประกอบ, ไอคอนหรือโลโก้แบบ raster, การแก้หรือย่อภาพด้วย AI) ถึงทีมจะมี agy ก็ตาม เพราะ agy ไม่มีเครื่องมือสร้างภาพ
> ใบงานภาพควรระบุให้ครบ: รายชื่อไฟล์ที่ต้องได้พร้อม path · ขนาดหรืออัตราส่วน · ฟอร์แมต · สไตล์ที่ทุกภาพต้องเหมือนกัน (ฉาก แสง มุมกล้อง พื้นหลัง) · สิ่งที่ห้ามมีในภาพ (ตัวหนังสือ โลโก้ มือคน) · และให้ Codex เปิดดูทุกภาพเอง ถ้าภาพไหนไม่ผ่านให้สร้างใหม่
> ถ้าภาพจะใช้บนเว็บ ให้สั่งทำเวอร์ชันย่อแยกจากต้นฉบับด้วย (เช่น JPEG 640px ไม่เกิน 120KB) · ก่อนรับงาน Claude ตรวจภาพทั้งชุดด้วย contact sheet · ตัวอย่างจริง: รูปสินค้า 12 ภาพสไตล์เดียวกันเสร็จในรอบเดียว

สคริปต์ช่วย: `scripts/codex-run.sh` (preflight + run ที่ใส่ flag ถูกต้องให้อัตโนมัติ) ใช้ได้ทุกเครื่อง macOS/Linux/WSL ที่มี Codex CLI
อ่านเพิ่มเมื่อจำเป็น:
- `references/codex-cli-guide.md` — โมเดล อัตราเครดิต คำสั่ง config, AGENTS.md, CI (อ่านเมื่อต้องตั้งค่า/เลือกโมเดลยาก/ทำ automation)
- `references/task-sheet.md` — เทมเพลตใบงาน + ตัวอย่างดี/แย่ (อ่านก่อนเขียนใบงานแรกของ session)
- `references/model-roles.md` — โมเดลตามบทบาทในทีม (Architect/Dev/UI QA/QA/Reviewer/DevOps/Maintainer/Image maker) + หลักฐานที่ต้องเห็นก่อนรับงาน, ตัวอย่างแบ่ง ticket, การส่งต่องานระหว่างโมเดล, Codex vs agy (อ่านเมื่อแบ่งงานหลายบทบาทหรือไม่แน่ใจว่าจะใช้โมเดลไหน)

## 1. Preflight ครั้งเดียวต่อ session (ถูกมาก ป้องกันงานใหญ่ล้มกลางทาง)

```bash
bash <skill-dir>/scripts/codex-run.sh preflight
```

ตรวจ: มี `codex` ไหม, เวอร์ชัน, login แบบไหน (ChatGPT = ใช้โควตาแพ็กเกจ / API key = คิดเงินตาม Platform), โมเดลที่บัญชีใช้ได้, และโมเดลใน `~/.codex/config.toml` ใช้ได้จริงหรือไม่
- ถ้าโมเดลใน config ไม่อยู่ในรายการ → **อย่าแก้ config ของผู้ใช้เอง** ให้ส่ง `-m` ทุกครั้งแทน แล้วบอกผู้ใช้
- ถ้ายังไม่ login → ให้ผู้ใช้รัน `codex login` เอง (เปิดเบราว์เซอร์; SSH ใช้ `codex login --device-auth`) Claude ห้ามกรอกรหัสผ่าน/API key แทน
- ถ้าเครื่องไม่มี `codex`: `npm install -g @openai/codex` (ต้องมี Node.js) — ถามผู้ใช้ก่อนติดตั้ง

## 2. เลือกโมเดลและ reasoning ให้พอดีงาน

| งาน | โมเดล | reasoning |
|---|---|---|
| งานซ้ำที่มีตัวอย่างก่อน–หลัง + คำสั่งยืนยัน (เติม fixture ตามตาราง, แก้ข้อความตามแพตเทิร์น) | `gpt-6-luna` | **`high`** (OpenAI แนะนำเริ่ม Luna ที่ high) |
| งานสั้นขอบเขตชัดมาก | `gpt-6.2-sol` | `low` |
| ตรวจ UI จากภาพหน้าจอ เทียบกับแบบ (`-i shot.png`, `-s read-only`) | `gpt-6.1-terra` | `low`–`medium` (ราคา 0.5× Sol) |
| พัฒนาทั่วไป (ฟีเจอร์ขนาดพอดี แก้บั๊ก รีวิว PR, **สร้างภาพ**) — **ค่าเริ่มต้น** | `gpt-6.2-sol` | `medium` |
| หลายไฟล์ ต้องไล่ data flow / regression หลายชั้น | `gpt-6.2-sol` | `high` |
| ผลกระทบสูง หลายสมมติฐาน (ข้ามบริการ, concurrency, migration ข้อมูล) | `gpt-6.2-astra` | เริ่ม `medium` |

ความเร็วใช้ **Standard** เสมอเมื่อเน้นโควตา (Fast กินโควตา ~2 เท่าสำหรับ Sol) Astra แพงกว่า Sol ~4 เท่าต่อโทเคน → ใช้เฉพาะเมื่อ Sol ติดแล้ว โดยส่ง "อาการ + สมมติฐานที่ตัดทิ้งแล้ว + คำสั่งที่ลอง" ให้ Astra วินิจฉัยเฉพาะจุดที่ค้าง ไม่ใช่โยนงานทั้งก้อนใหม่
รายการโมเดลต่างกันตามบัญชี/เวลา — เชื่อผล preflight มากกว่าตารางนี้

## 3. เขียนใบงาน (ส่วนที่ประหยัดโควตาได้มากที่สุด)

ใบงานที่ดีทำให้ Codex ไม่ต้องสำรวจทั้ง repo และจบในรอบเดียว ใช้โครงนี้ (รายละเอียดใน `references/task-sheet.md`):

```text
เป้าหมาย — พฤติกรรมที่ผู้ใช้ควรเห็น
หลักฐาน — path/ฟังก์ชัน/คำสั่งที่พัง + error ส่วนสำคัญ (ตัดข้อมูลลับออก)
ขอบเขต — ไฟล์ที่แก้ได้ และสิ่งที่ต้องรักษา (API, ข้อมูลเดิม, งานของคนอื่น)
เกณฑ์ผ่าน — อินพุต → ผลลัพธ์ที่คาด + กรณีขอบ
การตรวจ — เทสต์เจาะจุดก่อน แล้วชุดที่เกี่ยวข้อง
ส่งมอบ — สรุปไฟล์ที่แก้ เหตุผล คำสั่งที่รัน ผลทดสอบจริง; ยังไม่ต้อง commit
```

หลักคิด:
- **1 ใบงาน = 1 ผลลัพธ์ = 1 ชุดไฟล์** diff จะเล็กและตรวจง่าย งานจัดโครงสร้างแยกจากงานแก้บั๊ก
- **ชี้ ไม่ใช่แปะ** — บอก path และชื่อฟังก์ชันให้ Codex อ่านเอง แทนการแปะโค้ดยาว ๆ
- **ระบุค่าจริง** (px, hex, ตัวเลขที่คาด) ดีกว่าคำกว้าง ๆ อย่าง "ทำให้สวยขึ้น"
- **บั๊ก: ให้เทสต์ล้มก่อนแก้** แล้วผ่านหลังแก้ — เป็นหลักฐานว่าแก้ถูกจุด
- งานใหญ่หลายทางเลือก: สั่งรอบแรกเป็น `-s read-only` ให้เสนอแผน + ผลกระทบ + แผนทดสอบ ก่อนอนุญาตลงมือ
- ถ้า repo มี `AGENTS.md` Codex อ่านเองอยู่แล้ว ไม่ต้องทวนกติกาซ้ำในใบงาน (ประหยัด input) — ถ้าไม่มีและจะสั่งงานหลายรอบ เสนอผู้ใช้สร้าง `AGENTS.md` สั้น ๆ (ดู reference)
- เก็บใบงานเป็นไฟล์ (เช่น `tasks/NN-name.md`) แล้วสั่งสั้น ๆ ว่า "ทำใบงาน tasks/NN-name.md" — ใบงานจะถูกเก็บไว้ตรวจย้อนหลังและใช้ซ้ำได้

## 4. รัน

```bash
bash <skill-dir>/scripts/codex-run.sh run \
  --dir /path/to/repo \
  --model gpt-6.2-sol --effort medium \
  --sandbox workspace-write \
  --task-file tasks/03-fix-zero-price.md        # หรือ --prompt "..."
  # --image shot1.png --image shot2.png          # แนบภาพหน้าจอได้
```

สคริปต์จัดการกับดักที่เจอบ่อยให้แล้ว: ใส่ `--` คั่นก่อน prompt (ไม่งั้น `-i` จะกลืน prompt เป็นชื่อไฟล์), ป้อน stdin เป็น `/dev/null` (ไม่งั้น exec ค้างรอ stdin), ใส่ `--skip-git-repo-check` เมื่อไม่ใช่ git repo, บันทึก log + คำตอบสุดท้าย (`-o`) ไว้ใน `.codex-runs/` ของ repo, และพิมพ์ `git status/diff --stat` ให้หลังจบ
- งานยาว: รันแบบ background แล้วรอการแจ้งเตือน อย่า poll ถี่ ๆ
- งานคนละไฟล์กันรันขนานได้ งานที่แตะไฟล์เดียวกันต้องรันต่อกัน (กันเขียนทับ) หรือใช้ `--worktree`
- sandbox: `read-only` สำหรับสำรวจ/รีวิว/วางแผน, `workspace-write` สำหรับแก้โค้ด ห้ามใช้ `--dangerously-bypass-approvals-and-sandbox` เว้นแต่ผู้ใช้สั่งชัดเจนและเข้าใจความเสี่ยง
- ใน `codex exec` ไม่มี `-a` (ไม่มีใครกดอนุมัติ — คำสั่งที่ sandbox ไม่ยอมจะ fail กลับไปให้โมเดล) ถ้างานต้องใช้ network/ติดตั้ง dependency ให้ระบุในใบงานว่าห้ามติดตั้ง หรือให้ผู้ใช้รันแบบ interactive เอง

## 5. ตรวจงาน — Claude เป็นผู้ตัดสิน ไม่ใช่ Codex

รายงานของ Codex คือคำกล่าวอ้าง ยังไม่ใช่หลักฐาน ก่อนบอกผู้ใช้ว่าเสร็จ:
1. `git status --short` — ดูไฟล์ใหม่ด้วย (`git diff` ปกติไม่โชว์ไฟล์ untracked) และดูว่าไม่มีไฟล์นอกขอบเขตโดนแก้
2. `git diff --check` + อ่าน `git diff` เฉพาะส่วนที่เกี่ยว
3. **รันเทสต์เอง** (เจาะจุดก่อน แล้วชุดที่เกี่ยว) — ถ้าเป็น UI ให้เปิดดู/วัดในเบราว์เซอร์จริง เพราะ Codex ใน sandbox มักเปิดเบราว์เซอร์ไม่ได้และจะบอกเองว่า "ยังยืนยันไม่ได้"
4. ถ้าอยากได้ความเห็นที่สอง: `codex review --uncommitted` (หรือ `--base main`) — ถือ finding เป็นจุดเริ่มตรวจ ไม่ใช่ข้อสรุป; `codex review` ไม่มี `-m` ใช้ `-c model="gpt-6.2-sol"` แทน
5. รวมจุดที่ต้องแก้ทั้งหมดเป็น **ใบงานแก้รอบเดียว** แทนการสั่งแก้ทีละข้อ

Commit/push เฉพาะเมื่อผู้ใช้สั่ง; stage เป็นรายไฟล์ แล้วดู `git diff --cached` ก่อน commit

## 6. คุมโควตา — สรุปสั้น

- preflight ก่อน, smoke test 1 บรรทัดก่อนงานใหญ่ เมื่อเปลี่ยนโมเดล/flag
- Standard speed, เริ่ม Sol/medium, ขยับขึ้นเมื่อมีหลักฐานว่าต้องการ
- ใบงานชี้ path แทนแปะโค้ด, ขอบเขตแคบ, เกณฑ์ผ่านชัด
- เทสต์เจาะจุดก่อนชุดใหญ่
- รวมการแก้เป็นรอบเดียว; ถ้ารอบที่สองยังไม่ผ่าน หยุดวิเคราะห์สาเหตุก่อนสั่งรอบสาม
- ก่อนสั่งงานที่น่าจะกินโควตามาก (Astra, high reasoning, งานทั้ง repo) บอกผู้ใช้ก่อน
- จดใน log ว่ารอบไหนใช้ tokens เท่าไร (`tokens used` ท้าย output) เพื่อเทียบความคุ้มของโมเดลกับงานประเภทเดียวกัน

## 7. กับดักที่เจอจริง

| อาการ | สาเหตุ | ทางแก้ |
|---|---|---|
| `model ... is not supported when using Codex with a ChatGPT account` | config ชี้โมเดลเก่า | ส่ง `-m` ที่ preflight บอกว่าใช้ได้ |
| `No prompt provided via stdin` ทั้งที่ใส่ prompt | `-i` รับหลายค่าแล้วกลืน prompt | ใส่ `--` ก่อน prompt (สคริปต์ทำให้แล้ว) |
| exec ค้างเฉย ๆ / `Reading additional input from stdin` | stdin ไม่ปิด | `< /dev/null` (สคริปต์ทำให้แล้ว) |
| `Not inside a trusted directory` / ต้องการ git | ไม่ใช่ git repo | `--skip-git-repo-check` (สคริปต์ใส่ให้อัตโนมัติ) |
| เขียนไฟล์ไม่ได้ `Operation not permitted` บน macOS | โฟลเดอร์ที่ OS ปกป้อง (Downloads/Desktop/Documents) | ทำงานใน `~/Projects/...` หรือให้ผู้ใช้เปิดสิทธิ์ Files & Folders เอง |
| Codex บอก "เปิดเบราว์เซอร์ไม่ได้ ยังยืนยัน UI ไม่ได้" | sandbox | Claude ตรวจ UI เองในเบราว์เซอร์ หรือแนบภาพหน้าจอด้วย `--image` |
